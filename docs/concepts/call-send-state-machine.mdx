---
title: "The useContractCall / useContractSend state machine"
description: "Why a send exposes a status field instead of a boolean isLoading"
---

Contract calls and sends have fundamentally different lifecycles. Soroform's two hooks reflect that instead of flattening both into the same shape.

## Calls: simulation only

`useContractCall` is a thin TanStack Query wrapper. It has exactly the states TanStack Query already gives you: `isLoading`, `isError`, `data`, `error`. A call never needs a wallet, since it only simulates the method and decodes the result; it never signs or sends anything.

```tsx
const { data, isLoading, error } = useContractCall<bigint>({
  contractId,
  method: "balance",
  args: { id: address },
});
```

## Sends: a five-phase state machine

A send has to build a transaction, simulate it, get it signed, and send it, each of which can fail independently and each of which a UI usually wants to render differently (disable a button while simulating, show a wallet prompt while waiting on a signature, show a spinner while submitting). A single boolean cannot express that, so `useContractSend` exposes a literal `status` field instead:

```ts
type ContractSendStatus =
  | "idle"
  | "simulating"
  | "needsSignature"
  | "submitting"
  | "success"
  | "error";
```

<Steps>
  <Step title="idle">
    Before `sendAsync` has been called, or after `reset()`.
  </Step>
  <Step title="simulating">
    The contract's spec is fetched (or read from cache), args are validated, and the transaction is built and simulated via `AssembledTransaction.build`.
  </Step>
  <Step title="needsSignature">
    The transaction has been simulated and is ready to sign. This is when a wallet extension's approval popup typically appears.
  </Step>
  <Step title="submitting">
    The signed transaction has been sent to the network and Soroform is waiting for a result.
  </Step>
  <Step title="success">
    The transaction succeeded. `data` holds the decoded return value, via `spec.funcResToNative`.
  </Step>
  <Step title="error">
    Any of the above steps threw. `error` holds a normalized `SoroformError` (see [Error handling](/concepts/error-handling)).
  </Step>
</Steps>

A typical render:

```tsx
const { status, data, error, sendAsync } = useContractSend<boolean>({
  contractId,
  method: "transfer",
});

return (
  <button
    disabled={status === "simulating" || status === "submitting"}
    onClick={() => sendAsync({ to, amount: 100n })}
  >
    {status === "needsSignature" && "Confirm in your wallet..."}
    {status === "submitting" && "Sending..."}
    {(status === "idle" || status === "success" || status === "error") && "Transfer"}
  </button>
);
```

## What happens on success

On a successful send, Soroform invalidates every `useContractCall` query for that contract (`queryClient.invalidateQueries` against the `queryKeys.contractCallsByContract` prefix), so any call hooks watching that contract refetch automatically. You do not need to manually refetch a balance after a transfer.

## Requires a connected wallet

`useContractSend` reads `address`, `signTransaction`, and `signAuthEntry` from `useWallet()` (see [`useWallet`](/hooks/use-wallet)). If no wallet is connected, the underlying SDK call fails with a normalized error rather than silently no-oping.
