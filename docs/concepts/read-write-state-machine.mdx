---
title: "The useContractRead / useContractWrite state machine"
description: "Why writes expose a status field instead of a boolean isLoading"
---

Contract reads and writes have fundamentally different lifecycles. Soroform's two hooks reflect that instead of flattening both into the same shape.

## Reads: simulation only

`useContractRead` is a thin TanStack Query wrapper. It has exactly the states TanStack Query already gives you: `isLoading`, `isError`, `data`, `error`. A read never needs a wallet, since it only simulates the call and decodes the result; it never signs or sends anything.

```tsx
const { data, isLoading, error } = useContractRead<bigint>({
  contractId,
  method: "balance",
  args: { id: address },
});
```

## Writes: a five-phase state machine

A write has to build a transaction, simulate it, get it signed, and send it, each of which can fail independently and each of which a UI usually wants to render differently (disable a button while simulating, show a wallet prompt while waiting on a signature, show a spinner while submitting). A single boolean cannot express that, so `useContractWrite` exposes a literal `status` field instead:

```ts
type ContractWriteStatus =
  | "idle"
  | "simulating"
  | "needsSignature"
  | "submitting"
  | "success"
  | "error";
```

<Steps>
  <Step title="idle">
    Before `writeAsync` has been called, or after `reset()`.
  </Step>
  <Step title="simulating">
    The contract's spec is fetched (or read from cache), args are validated, and the transaction is built and simulated via `AssembledTransaction.build`.
  </Step>
  <Step title="needsSignature">
    The transaction has been simulated and is ready to sign. This is when a wallet extension's approval popup typically appears.
  </Step>
  <Step title="submitting">
    The signed transaction has been sent to the network and Soroform is waiting for a result.
  </Step>
  <Step title="success">
    The transaction succeeded. `data` holds the decoded return value, via `spec.funcResToNative`.
  </Step>
  <Step title="error">
    Any of the above steps threw. `error` holds a normalized `SoroformError` (see [Error handling](/concepts/error-handling)).
  </Step>
</Steps>

A typical render:

```tsx
const { status, data, error, writeAsync } = useContractWrite<boolean>({
  contractId,
  method: "transfer",
});

return (
  <button
    disabled={status === "simulating" || status === "submitting"}
    onClick={() => writeAsync({ to, amount: 100n })}
  >
    {status === "needsSignature" && "Confirm in your wallet..."}
    {status === "submitting" && "Sending..."}
    {(status === "idle" || status === "success" || status === "error") && "Transfer"}
  </button>
);
```

## What happens on success

On a successful write, Soroform invalidates every `useContractRead` query for that contract (`queryClient.invalidateQueries` against the `queryKeys.contractReadsByContract` prefix), so any read hooks watching that contract refetch automatically. You do not need to manually refetch a balance after a transfer.

## Requires a connected wallet

`useContractWrite` reads `address`, `signTransaction`, and `signAuthEntry` from `useWallet()` (see [`useWallet`](/hooks/use-wallet)). If no wallet is connected, the underlying SDK call fails with a normalized error rather than silently no-oping.
