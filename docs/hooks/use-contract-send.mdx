---
title: "useContractSend"
description: "Build, simulate, sign, and send a state-changing contract method call"
---

Builds, simulates, signs, and sends a state-changing contract method call, exposing the full lifecycle as a `status` field rather than a single boolean. Requires a connected wallet. See [The useContractCall / useContractSend state machine](/concepts/call-send-state-machine) for the full phase-by-phase breakdown.

```ts
import { useContractSend } from "@sorokit/contract";

function useContractSend<TResult = unknown>(
  options: UseContractSendOptions,
): UseContractSendResult<TResult>;
```

## Parameters

| Name         | Type              | Required | Description                                                |
| ------------ | ----------------- | -------- | ---------------------------------------------------------- |
| `contractId` | `string`          | Yes      | The deployed contract's address (`C...`).                  |
| `method`     | `string`          | Yes      | The state-changing method to call.                         |
| `network`    | `SorokitNetwork` | No       | Overrides the network from the nearest `SorokitProvider`. |

## Return value

| Field       | Type                                                                                             | Description                                                                |
| ----------- | ------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------- |
| `status`    | `"idle" \| "queued" \| "simulating" \| "needsSignature" \| "submitting" \| "success" \| "error"` | The current phase.                                                         |
| `data`      | `TResult \| undefined`                                                                           | The decoded result, once `status` is `"success"`.                          |
| `error`     | `SorokitError \| undefined`                                                                     | A normalized error, once `status` is `"error"`.                            |
| `hash`      | `string \| undefined`                                                                            | The transaction hash, from the moment the network accepts it.              |
| `sendAsync` | `(args?: Record<string, unknown>) => Promise<TResult>`                                           | Validates args, simulates, signs, and sends.                               |
| `reset`     | `() => void`                                                                                     | Resets `status`, `data`, `error`, and `hash` back to their initial values. |

## Example

```tsx
import { useContractSend } from "@sorokit/contract";

function TransferButton({ contractId, to }: { contractId: string; to: string }) {
  const { status, sendAsync, error } = useContractSend<boolean>({
    contractId,
    method: "transfer",
  });

  return (
    <div>
      <button
        disabled={status === "simulating" || status === "submitting"}
        onClick={() => sendAsync({ to, amount: 100n })}
      >
        {status === "idle" || status === "success" ? "Transfer" : status}
      </button>
      {error && <p>{error.message}</p>}
    </div>
  );
}
```

## Sequence numbers and concurrent sends

A Stellar transaction carries a sequence number that must be exactly one past the account's current one. Two sends assembled at the same time — a double-clicked button, or two components each firing one — would otherwise both read the same account state, claim the same number, and the second to land would fail with `tx_bad_seq`.

Every send is queued through a global sequencer keyed by the connected wallet address, so this is handled for you with no configuration. Sends from one account are assembled one at a time, and the sequence number is projected forward as each transaction is accepted rather than re-read from a ledger that has not closed yet — so a burst of sends goes out back to back instead of one per ~5 second ledger close. A send waiting its turn reports `status: "queued"`.

The one thing this trades away: a queued send is simulated against a ledger that does not yet contain the send ahead of it. That is fine for repeated independent calls, and wrong only when a call's storage footprint or authorization depends on what the previous call wrote — in that case, `await` the first `sendAsync` before starting the second.

## Surviving a page reload

Once the network accepts a transaction it is recorded in a queue mirrored into `localStorage`. If the page is reloaded while a send is `"submitting"`, [`SorokitProvider`](/components/sorokit-provider) picks the transaction back up on mount, polls for its outcome, and invalidates the contract's cached reads once it lands. Nothing needs to be wired up for this; entries that never land age out of the queue on their own.

## Caching and invalidation

On success, every [`useContractCall`](/hooks/use-contract-call) query for the same `contractId` is invalidated automatically, so calls reflect the new state without a manual refetch. See [Query key and cache invalidation model](/concepts/query-keys-and-caching).

## Devtools logging

In development (`process.env.NODE_ENV === "development"`), every status transition is recorded to `@sorokit/core`'s `devtoolsSendLog` store, which [`SorokitDevtools`](/components/sorokit-devtools) reads from. This has no effect if `@sorokit/devtools` is not installed.
